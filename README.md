# WorkBuddy 多账号自动签到工具（独立版）

一次运行，把 **N 个账号**的「Buddy 加油站」每日签到 + **派小猫旅行** + **活跃自检（连登预警）** + **每日问候**全部跑完。
Token 存在工具自己的 `accounts.json` 里，**运行期不读取、不依赖 WorkBuddy 客户端**——客户端没开、没登录、登录态被本地加密，都不影响。

> **从 GitHub 克隆后怎么开始**：仓库**不含** `accounts.json`（含明文 Token，已被 `.gitignore` 排除），首次运行会自动生成空配置。
> 你只需要：① 在本机登录过要签到的账号 → ② 双击 `启动菜单.bat` → ③ 选 `8 → 1` 提取 Token → ④ 选 `1` 试跑一次 → ⑤ 选 `9 → 1` 装上每日定时任务。全程不用记命令。

```
wb-checkin-multi/
├─ 启动菜单.bat            ★ 双击即用（交互式菜单，不用记任何命令）
├─ wb_menu.py             菜单程序（CLI 向导）
├─ wb_checkin_multi.py    主程序 / 命令行（纯 Python 标准库，零依赖，Python 3.6+）
├─ install_task.ps1       Windows 计划任务安装/卸载（签到任务 + 问候任务，独立于 WorkBuddy）
├─ test_greet_logic.py    问候逻辑离线单测（随机时刻/多语言/幂等/窗口判定，不联网）
├─ accounts.json          账号与 Token（首次运行自动生成；含明文凭据，勿外传）
├─ accounts.example.json  配置模板
└─ logs/
   ├─ checkin-YYYY-MM.csv  每日明细（按账号一行，可直接用 Excel 打开）
   ├─ last_run.json        最近一次运行的完整结果（含 activity 活跃自检明细）
   ├─ greet_state.json     今日问候状态（随机时刻 + 各账号发送结果）
   └─ greet_trace.log      问候轮询留痕（计划任务每次「发/跳过」都记一行）
```

## ⚠️ 关于「每日问候」的说明（v1.0.3 起默认开启）

v1.0.3 新增了一个**会主动向模型发起对话**的功能：每天在 `03:00-08:00` 之间随机一个时刻，用 `hy3` 模型为每个账号发一条**随机语言**的问候（汉语/英语/俄语/法语/意大利语/德语），目的是把活跃地图点亮、维持连登。

需要明确的是：

- 该活动条款写明「**严禁采用刷量、多账号套利、篡改数据等作弊行为**」「**非正常使用路径触发风控**，平台有权取消领取资格并回收对应奖励权益」。
- 用脚本自动发对话属于**自动化发起对话**，存在被判定为「非正常使用路径」的风险。风险由使用者自行评估与承担。
- **一键回到纯检测模式**：命令行加 `--no-greet`，或在菜单里改用不含问候的执行项。关闭后本工具不会向任何模型接口发请求。
- 该功能**默认开启**，是因为它由使用者明确要求并知情；如果你不需要，请立刻用 `--no-greet` 关掉。

下面「[每日问候](#每日问候v103-新增)」一节是完整实现说明与取舍记录。

## 方式二：命令行（适合脚本 / 定时任务）

### 快速开始（3 步）

```bash
# 1) 提取本机 History 登录态里的 Token（一次性，只读，按账号自动归组）
python wb_checkin_multi.py --capture

# 2) 核对账号与 Token 有效期
python wb_checkin_multi.py --list

# 3) 全部账号签到 + 派小猫 + 活跃自检 + 每日问候（并发执行）
python wb_checkin_multi.py

# 3b) 如果不想让它自动发问候（纯签到，不向模型发起任何对话）
python wb_checkin_multi.py --no-greet
```

安装每日自动执行（**与 WorkBuddy 无关，系统级定时**）：

```powershell
powershell -ExecutionPolicy Bypass -File install_task.ps1            # 09:00 签到 + 03:00-08:00 问候轮询
powershell -ExecutionPolicy Bypass -File install_task.ps1 -Time 09:10
powershell -ExecutionPolicy Bypass -File install_task.ps1 -SkipGreet  # 只装签到任务
powershell -ExecutionPolicy Bypass -File install_task.ps1 -OnlyGreet  # 只装问候任务
powershell -ExecutionPolicy Bypass -File install_task.ps1 -Uninstall  # 两个一起卸载
```

会注册**两个**任务：

| 任务名 | 触发 | 跑什么 |
|---|---|---|
| `WorkBuddy-MultiCheckin` | 每日 09:00 | 完整流程（含问候的「错过补发」） |
| `WorkBuddy-Greet` | 每日 03:00 起每 15 分钟一次，持续 5 小时 | `--greet-window`：到当天随机时刻才发，否则静默退出 |

> 计划任务跑的是**无参数模式**（问候任务用 `pythonw.exe`，不弹控制台窗口），不会弹出交互界面，与菜单互不干扰。

## 账号管理

| 操作 | 命令 |
|---|---|
| 从本机登录态批量提取 | `--capture`（可选 `--capture-dir 目录`、`--label-prefix 公司`、`--keep-label`） |
| 手工添加账号 | `--add --label 小号 --token <TOKEN> [--domain www.workbuddy.cn]`（省略 `--token` 则交互式粘贴） |
| 更新既有账号 Token | `--set-token 小号 [--token <TOKEN>] [--domain ...]` |
| 启用 / 停用账号 | `--enable 小号` / `--disable 小号` |
| 删除账号 | `--remove 小号` |
| 设置固定派遣地点 | `--set-location 小号 --set-location-value 3`（`random` 表示随机） |
| 查看账号与有效期 | `--list` |
| 桌面通知开关（持久化） | `--notify on` / `--notify off` |

`--capture` 的取用规则（多账号场景的关键）：

1. 扫描 `%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop*.info`（历史快照一并扫描）；
2. 按顶层 `account.uid` **分组**——同一台机器上多个账号登录过，快照会交替属于不同账号，不分组就会把 A 的 Token 配到 B 名下；
3. 每组取**未过期且最新**的一份明文 Token；
4. 账号名优先用快照里的昵称，昵称被加密时回落到 `账号-<uin 后四位>`。

> `--capture` 只读不写：修改的只有本工具的 `accounts.json`，登录态文件分毫不动。

## 派小猫旅行（每个账号独立闭环）

1. 查状态 `GET /activity/growth/buddy/travel/status`；
2. `arrived`（已到达）→ `POST .../travel/claim` 领积分，再复查状态；
3. `idle` 且**未达每日上限** → `POST .../travel/depart` 派出（随机地点，或指定）；
4. `traveling` → 不派遣，只报到达倒计时；**已到达的奖励不会丢**，下次运行自动补领。

硬规则：派遣前必查 `daily_limit_reached`，达上限**一个写请求都不发**。
旅行接口域名固定 `www.workbuddy.cn` 且路径**不带 `/v2`**（用签到域名或加 `/v2` 一律 404）。

## 活跃自检与连登预警（v1.0.2 新增）

### 「签到」和「连登」是两套独立机制，别混为一谈

| | 签到 | 连登（streak / 活跃地图） |
|---|---|---|
| 接口 | `POST /v2/billing/meter/daily-checkin` | `GET /v2/activity/growth/streak`、`GET /v2/activity/growth/heatmap` |
| 给什么 | Credits（通用积分） | 决定 7 / 14 / 28 天档位的兑换奖励与补登卡 |
| 判定口径 | 手动/自动点「领取」 | **当天需完成一次有效对话** |
| 数据刷新 | 即时 | 活跃地图「每日 02:00」聚合 |

口径来源于成长计划页内置的官方文案（非推测）：

> 「活跃口径：需完成一次有效对话才能被记录至活跃地图。」
> 「为判定用户任务完成状态、计算能量值及积分（Credit），腾讯云需要收集：（1）**AI 对话次数**；…」

**结论：只跑签到脚本并不能保住连登。** 某天完全没用 WorkBuddy，活跃地图当天记 0 分，连登就断。

### 本工具怎么做

只读拉两个接口，逐账号报出「今日是否点亮 + 活跃分 + 连登天数」：

```
GET https://www.workbuddy.cn/v2/activity/growth/heatmap
    → data.today = {date, score, is_active, status_text}
GET https://www.workbuddy.cn/v2/activity/growth/streak
    → data.streak = {days, month_total_days, next_tier, makeup_dates}
```

活跃分档位（对齐前端配色函数）：`0` 未点亮 ｜ `≤10` 微亮 ｜ `≤30` 常亮 ｜ `≤60` 高亮 ｜ `>60` 炽热。
**当天未点亮时**，报告会打印 `⚠ 连登预警`，桌面通知标题也会变成「活跃预警：N 个账号今日未点亮」，并点名要手动处理的账号。

### v1.0.2 时的取舍 → v1.0.3 已改变

v1.0.2 时本工具在活跃维度**只做检测与提醒、不代发对话**，理由是活动条款明确写着：

> 「合规性要求：用户需通过正常使用路径参与活动，**严禁采用刷量、多账号套利、篡改数据等作弊行为**。一经系统识别，立即取消获奖资格，追回已发礼品。」
> 「如因账号异常、作弊行为、批量注册或**非正常使用路径触发风控**，平台有权取消领取资格并回收对应奖励权益。」

## 每日问候（v1.0.3 新增）

### 它解决什么问题

连登（活跃地图）的判定口径是「当天完成一次有效对话」。只签到保不住连登（见上节）。问候功能就是**每天自动完成一次有效对话**。

### 接口契约（实测确认，勿随意改动）

```
POST https://<domain>/v2/chat/completions
Authorization: Bearer <accessToken>
Content-Type: application/json
Accept: text/event-stream

{"model": "hy3", "stream": true,
 "messages": [{"role": "user", "content": "<问候语>"}]}
```

三个关键实测结论：

1. **必须 `stream: true`。** 非流式请求会被服务端直接拒掉，返回 `HTTP 400 / code=11101 / "Non-stream chat request is currently not supported"`。这个报错的文案有误导性（像是在说鉴权或参数缺失），**实际只跟 stream 有关**。
2. **请求头只需要 `Authorization` + `Content-Type` + `Accept`。** 不需要复刻客户端的网关头（`X-User-Id` / `X-Enterprise-Id` / `X-Conversation-*` / traceparent 三件套等）——那些是客户端自己代理链路用的，直连一方网关时非必需。
3. **必须把流读到底。** 读完才能拿到 `finish_reason` 与 `usage`；半途关流可能拿不到结算信息。

### 随机问候：6 种语言 × 30 条候选

| 语言 | 候选条数 | 示例 |
|---|---|---|
| 汉语 | 5 | 你好 / 早上好 / 新的一天开始了 |
| 英语 | 5 | Hello / Good morning / Morning! Have a nice day |
| 俄语 | 5 | Привет / Доброе утро / Здравствуйте |
| 法语 | 5 | Bonjour / Salut / Bonne matinée |
| 意大利语 | 5 | Ciao / Buongiorno / Salve |
| 德语 | 5 | Hallo / Guten Morgen / Moin |

每次随机取「语言 × 句子」，**优先挑最近没用过的组合**（历史保留 12 条），避免连着几天都是同一句。六种语言等概率。

想看随机效果又不想真的发送：菜单 `6 → 3`。

### 随机时间：03:00-08:00

- 每天在 `03:00-08:00` 内**均匀随机**取一个时刻（精确到分钟），写入 `logs/greet_state.json`，**当天固定不变**。
- 由计划任务 `WorkBuddy-Greet` 在窗口内每 15 分钟轮询一次：到点就发，没到就静默退出（只往 `logs/greet_trace.log` 写一行）。
- 幂等：当天已成功发送的账号不会重复发送；发送失败会在后续轮询中重试，最多 3 次。

### 错过补发（重要）

本机实测**常在 08:14-10:04 才开机**（近 14 天开机记录：09-30 10:04、09-30 08:22、09-29 08:22、09-23 08:14…），
也就是 `03:00-08:00` 窗口**经常整段错过**。若严格只在窗口内发送，这个功能大部分日子都不会生效。

因此默认开启**补发**：窗口过后若当天仍未发送，会在下一次运行时（通常是 09:00 的签到任务）补发，并在报告 / CSV 中标注「补发」。

- 关闭：`--no-greet-catchup`，或菜单 `12 → 4`。关闭后严格只在窗口内发送，错过就当天不发。
- 若想让窗口内必定生效，可在计划任务里勾选「唤醒计算机运行此任务」（代价是机器会被定时唤醒）。

### 输出与留痕

| 位置 | 内容 |
|---|---|
| 终端报告 | 每账号一行：`问候：俄语「Здравствуйте」已发送（补发） ｜ 模型 hy3 ｜ 回复：…` |
| CSV | 新增 `问候语言 / 问候语 / 问候结果 / 问候回复` 四列 |
| `logs/greet_state.json` | 今日随机时刻 + 各账号发送结果（含回复摘要，**不含 Token**） |
| `logs/greet_trace.log` | 计划任务每次轮询的判定（投递 / 跳过及原因） |

### 刻意保留的边界

- **只发一条。** 每天每账号仅一次，不做「补足活跃分」之类的多轮刷量。
- **失败只重试 3 次**，不做无限重试。
- **绝不静默**：发送失败会在报告、CSV、桌面通知里点名。
- **随时可完全关闭**：`--no-greet` 之后本工具不会向任何模型接口发请求。

## 配置说明（`accounts.json`）

```json
{
  "version": 1,
  "settings": {
    "domains": ["www.workbuddy.cn", "www.codebuddy.cn"],
    "concurrency": 4,
    "travel_default": true,
    "desktop_notify": true,
    "greet_catchup": true,
    "greet_model": "hy3"
  },
  "accounts": [
    {
      "id": "acc1",
      "label": "张三",
      "uid": "…",
      "token": "<accessToken>",
      "domain": "www.workbuddy.cn",
      "enabled": true,
      "travel": true,
      "location_id": null

```

- `domains`：候选域名，按顺序探测（本机实测 `www.workbuddy.cn` 可用；`copilot.tencent.com` 在旧版快照里作过日志域名）。
- `enabled: false`：临时停用某账号（菜单 `8 → 4` 可切换，不删配置）。
- `location_id`：该账号固定派遣地点；填 `null` 走随机。
- `greet_catchup`：错过 `03:00-08:00` 窗口后是否在下次运行时补发问候。默认 `true`（菜单 `12 → 4`）。
- `greet_model`：问候所用模型，默认 `hy3`（菜单 `12 → 5`）。

## 排错速查

| 现象 | 原因与处置 |
|---|---|
| `Token 已失效或被拒绝（HTTP 401/403）` | Token 过期。登录该账号的 WorkBuddy 客户端 → 菜单 `8 → 1`（或 `--capture`）重新提取 |
| 菜单顶部显示 `Token：有 N 项需处理` | 有 Token 已过期或 7 天内到期，提前重新 capture 一次 |
| `无法连接签到接口（所有候选域名均失败）` | 内网/代理/防火墙；用菜单 `13` 看 DNS 是否解析成功 |
| `今日已签到，跳过领取` | 正常。服务端幂等，不会重复发积分 |
| `领取被服务端拒绝 code=10001 …（假已签到）` | **不正常，务必处理**：服务端在日边界对**未签到**的账号返回了「今天已签到」（读接口同期仍显示未签到）。v1.0.1 会先回查状态复核、再按 30/60/120 秒重试 3 次；若仍失败会明确报失败（退出码 1 + 桌面通知），此时需**手动补签**。旧版 v1.0.0 会把这种情况误当成功，请勿使用 |
| `今日派遣次数已用完，跳过派遣` | 正常的服务端每日限额，次日自动恢复 |
| `arrived` 状态一直不领 | 不会丢积分，下次运行自动补领 |
| CSV 里「已结算连签天数」比实际少 1 天 | 正常。该列取自状态接口，是**已结算口径**、当日入账可能滞后数分钟；判断当天签没签请只看 `状态/动作` 列或 `today_checked_in` |
| `⚠ 连登预警：以下账号今日未活跃` | 该账号当天还没在 WorkBuddy 里完成过一次有效对话，活跃地图没记分，连登会断档。默认已由每日问候自动点亮；若你关掉了问候（`--no-greet`），打开客户端任意对话发一条消息即可 |
| `活跃：自检失败 — 活跃地图接口不可用` | 该接口按账号鉴权，Token 失效或网络异常都会这样。签到结论不受影响；先按上一条排查 Token |
| `问候：发送失败 — HTTP 400 code=11101 …` | 该报错文案有误导性，**实际是 `stream` 参数问题**，不是鉴权。若你自己改过请求体，确认保留了 `"stream": true` |
| `问候：发送失败 — HTTP 401/403` | 该账号 Token 过期。签到可能仍正常（不同接口），按第一行处理 |
| `问候：本次不发送（未到今日随机时刻）` | 正常。当天随机时刻还没到，继续等下一轮轮询即可（`--greet-status` 可看具体时刻） |
| `问候：本次不发送（当天已发送）` | 正常，幂等生效。想强制重发用 `--greet-only --greet` |
| 问候一整天都没发出去 | ① 看 `logs/greet_trace.log` 的最后几行判定原因；② 本机常在 08:14 后才开机，窗口容易整体错过 —— 确认 `greet_catchup` 为开启；③ 检查 `WorkBuddy-Greet` 任务是否安装（菜单 `9 → 3`） |
| `--greet-only` 跑完显示「本次跳过」 | 正常，不是失败。当天已发过或未到点；退出码仍为 0 |
| CSV 里的 `今日活跃 / 活跃分 / 连登天数 / 问候*` 列是空的 | 该行写在**功能上线之前**。新列只会写进上线之后的记录；当前月份文件在首次写入时会自动补齐表头（并存一份 `.bak`），历史月份文件永不改动 |
| 菜单里中文显示成乱码 | 用 `启动菜单.bat` 启动（它会切到 UTF-8 代码页）；不要在旧版 cmd 里直接跑 |
| 菜单每次刷新都要等约 1 秒 | 首次查询计划任务状态会启动一次 PowerShell，结果缓存 20 秒，属正常 |
| 计划任务没跑 | 任务在当前用户上下文注册，需用户已登录；菜单 `9 → 3` 看上次执行时间与结果 |

## 安全约定

- `accounts.json` 含**明文 Token**，是本工具唯一的凭据文件：不要外传、不要提交到代码仓库、不要放进共享目录。
- 所有输出（终端 / CSV / JSON / 桌面通知）中的 Token 一律脱敏为 `eyJhbGci...xxxx`。
- 写操作仅限已验证端点：`daily-checkin`、`travel/claim`、`travel/depart`，
  以及 **`chat/completions`（v1.0.3 每日问候，可用 `--no-greet` 完全关闭）**。
  活跃自检（heatmap / streak）全程只读（GET）。
- `logs/greet_state.json` 会记录问候原文与模型回复摘要，**不含 Token**；如不想留痕，删除该文件即可（会重置当日状态）。
- 使用范围：**仅限本人账号**。

## 已知限制

- **Token 有效期约 30 天**，到期必须重新获取（本机实测 26 天左右）。这是接口鉴权的前提，无法绕过：
  桌面端 5.6+ 已把 accessToken / refreshToken 以 AES-256-GCM 静态加密存储，密钥只在客户端进程内存里、不落盘，离线无法解密。
  → 实用做法：每月登录一次客户端，跑一次 `--capture` 即可（工具会按账号自动择优更新）。
- 计划任务在「用户已登录」时触发；配合 `-StartWhenAvailable`，错过的执行会补跑一次。
- 旅行接口若被服务端下线，工具会静默降级，**不影响签到结论**。
- 未实现自动续期（refreshToken 同样被静态加密，无法离线使用）。
- **问候的窗口依赖机器开机**：`03:00-08:00` 若整段关机，窗口内不会发送，只能靠 `greet_catchup` 在之后第一次运行时补发。
  本机常在 `08:14-10:04` 开机，因此**实际发送时间多数会落在 09:00 前后**，真正的「3-8 点随机」只在机器整夜开机时生效。
  若要强制窗口内执行，可在计划任务里勾选「唤醒计算机运行此任务」。
- **活跃地图不是实时刷新**：官方口径为每日 02:00 聚合，但实测当天新增对话也会较快反映到 `score`。刚发完问候立刻查不一定能看到变化，属正常。
- 问候每次会消耗少量模型额度（实测 `hy3` 单次约 5 prompt + 30-50 completion tokens）。

## 更新日志

### v1.0.3（2026-10-01）

**新增**：每日问候 —— 解决「连登需要有效对话，而只签到保不住连登」的问题。

- 摸清并实测确认对话接口契约：`POST /v2/chat/completions`，`Authorization: Bearer <token>` 直连即可，**必须 `"stream": true`**（非流式会被服务端以 `code=11101 / "Non-stream chat request is currently not supported"` 拒绝，该文案有误导性），且必须把 SSE 流读到底才能拿到 `finish_reason` 与 `usage`。
- 新增随机问候：6 种语言（汉语/英语/俄语/法语/意大利语/德语）× 各 5 条候选 = 30 条；每次随机取「语言 × 句子」，**优先选最近没用过的组合**（历史保留 12 条），避免连日重复。
- 新增随机时间：每天在 `03:00-08:00` 内均匀随机取一个时刻（精确到分钟），持久化到 `logs/greet_state.json`，当天固定不变；由计划任务每 15 分钟轮询，到点才发。
- 新增**错过补发**：本机实测常在 `08:14-10:04` 才开机，纯窗口调度会整日错过；故窗口过后若当天仍未发送，会在下一次运行（如 09:00 签到任务）补发并标注「补发」。默认开启，`--no-greet-catchup` 可关闭。
- 新增幂等与重试上限：当天已成功的账号不再重复发送；失败在后续轮询中重试，最多 3 次。
- 新增计划任务 `WorkBuddy-Greet`（`install_task.ps1` 现一次装两个任务，支持 `-SkipGreet` / `-OnlyGreet`），问候轮询用 `pythonw.exe` 启动以避免凌晨弹控制台窗口。
- 新增开关：`--greet-only` / `--no-greet` / `--greet` / `--greet-window` / `--greet-status` / `--greet-reset` / `--greet-model` / `--no-greet-catchup`；菜单新增第 6 项「每日问候…」子菜单，原 6-13 项顺移为 7-14。菜单设置项新增「切换问候补发」「设置问候模型」。
- 新增留痕：`logs/greet_state.json`（今日状态）、`logs/greet_trace.log`（每次轮询判定）；CSV 新增 `问候语言 / 问候语 / 问候结果 / 问候回复` 四列。
- **CSV 表头升级策略改变**：v1.0.2 是「新列只进新月份文件」，导致当月文件一直缺列。v1.0.3 改为**缺列时向末尾追加**并补齐历史行（改前留 `.bak`）。只追加不重排，既有列位置与语义完全不变；历史月份文件仍永不打开写入。
- 修复两处自查发现的缺陷：① `greet_commit()` 持锁后重入同一把非重入锁导致**自死锁**（进程挂死、无输出，极易误判为网络问题）→ 改用 `threading.RLock()`；② 纯问候模式下「本次无需发送」被误判为失败（退出码 1）→ 改为 `status=ok / action=greet_skipped`。
- 新增**无控制台兜底**：计划任务用 `pythonw.exe` 时 `sys.stdout/stderr` 为 `None`，任何 `print()` 都会抛异常而静默失败；现自动接到 `logs/no_console_stdout.log`。
- 边界与风险：该功能会**主动发起对话**，活动条款禁止「刷量 / 非正常使用路径」，存在风控风险（详见文首说明）；`--no-greet` 可完全回到纯检测模式。

### v1.0.2（2026-09-30）

- 新增「未活跃」预警：报告打印 `⚠ 连登预警` 并点名账号，桌面通知标题改为「活跃预警」，正文提示「请手动发一条消息保住连登」。

### v1.0.1（2026-09-28）

**修复**：领取接口返回 `code=10001 / 已签到` 时不再直接当成功。

- **改前（v1.0.0）**：把该响应一律判为 `already_signed` 并静默结束 —— 一旦服务端在日边界返回了错的「已签到」（读接口同期仍显示未签到），当天就**漏签且无任何告警**，CSV / 通知 / 退出码全部报成功。
- **改后**：强制回查状态接口复核。复核也是已签 → 真幂等；复核仍是未签到 → 判为服务端「假已签到」，按 30/60/120 秒间隔重试（最多 4 次领取）；全部失败则 `status=error / action=rejected`，退出码 1 并在桌面通知中点名该账号，提示手动补签。
- 状态与领取接口的**原始 HTTP 码与响应体全部落盘**到 `logs/last_run.json` 的 `detail` 字段（改前恒为 `null`，事后无法定位），失败时也会打印到控制台。
- CSV 列名 `连续天数` → **`已结算连签天数`**（该字段为已结算口径，当日可能滞后）。
