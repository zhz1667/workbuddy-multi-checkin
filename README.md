# WorkBuddy 多账号自动签到工具（独立版）

一次运行，把 **N 个账号**的「Buddy 加油站」每日签到 + **派小猫旅行** + **活跃自检（连登预警）**全部跑完。
Token 存在工具自己的 `accounts.json` 里，**运行期不读取、不依赖 WorkBuddy 客户端**——客户端没开、没登录、登录态被本地加密，都不影响。

> **从 GitHub 克隆后怎么开始**：仓库**不含** `accounts.json`（含明文 Token，已被 `.gitignore` 排除），首次运行会自动生成空配置。
> 你只需要：① 在本机登录过要签到的账号 → ② 双击 `启动菜单.bat` → ③ 选 `7 → 1` 提取 Token → ④ 选 `1` 试跑一次 → ⑤ 选 `8 → 1` 装上每日定时任务。全程不用记命令。

```
wb-checkin-multi/
├─ 启动菜单.bat            ★ 双击即用（交互式菜单，不用记任何命令）
├─ wb_menu.py             菜单程序（CLI 向导）
├─ wb_checkin_multi.py    主程序 / 命令行（纯 Python 标准库，零依赖，Python 3.6+）
├─ install_task.ps1       Windows 计划任务安装/卸载（独立定时，不依赖 WorkBuddy）
├─ accounts.json          账号与 Token（首次运行自动生成；含明文凭据，勿外传）
├─ accounts.example.json  配置模板
└─ logs/
   ├─ checkin-YYYY-MM.csv  每日明细（按账号一行，可直接用 Excel 打开；v1.0.2 起新文件含活跃三列）
   └─ last_run.json        最近一次运行的完整结果（含 activity 活跃自检明细）
```

## 方式二：命令行（适合脚本 / 定时任务）

### 快速开始（3 步）

```bash
# 1) 提取本机 History 登录态里的 Token（一次性，只读，按账号自动归组）
python wb_checkin_multi.py --capture

# 2) 核对账号与 Token 有效期
python wb_checkin_multi.py --list

# 3) 全部账号签到 + 派小猫 + 活跃自检（并发执行）
python wb_checkin_multi.py
```

安装每日 09:00 自动执行（**与 WorkBuddy 无关，系统级定时**）：

```powershell
powershell -ExecutionPolicy Bypass -File install_task.ps1            # 默认 09:00
powershell -ExecutionPolicy Bypass -File install_task.ps1 -Time 09:10
powershell -ExecutionPolicy Bypass -File install_task.ps1 -Uninstall  # 卸载
```

> 计划任务跑的是**无参数模式**，不会弹出交互界面，与菜单互不干扰。

## 账号管理

| 操作 | 命令 |
|---|---|
| 从本机登录态批量提取 | `--capture`（可选 `--capture-dir 目录`、`--label-prefix 公司`、`--keep-label`） |
| 手工添加账号 | `--add --label 小号 --token <TOKEN> [--domain www.workbuddy.cn]`（省略 `--token` 则交互式粘贴） |
| 更新既有账号 Token | `--set-token 小号 [--token <TOKEN>] [--domain ...]` |
| 启用 / 停用账号 | `--enable 小号` / `--disable 小号` |
| 删除账号 | `--remove 小号` |
| 设置固定派遣地点 | `--set-location 小号 --set-location-value 3`（`random` 表示随机） |
| 查看账号与有效期 | `--list` |
| 桌面通知开关（持久化） | `--notify on` / `--notify off` |

`--capture` 的取用规则（多账号场景的关键）：

1. 扫描 `%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop*.info`（历史快照一并扫描）；
2. 按顶层 `account.uid` **分组**——同一台机器上多个账号登录过，快照会交替属于不同账号，不分组就会把 A 的 Token 配到 B 名下；
3. 每组取**未过期且最新**的一份明文 Token；
4. 账号名优先用快照里的昵称，昵称被加密时回落到 `账号-<uin 后四位>`。

> `--capture` 只读不写：修改的只有本工具的 `accounts.json`，登录态文件分毫不动。

## 派小猫旅行（每个账号独立闭环）

1. 查状态 `GET /activity/growth/buddy/travel/status`；
2. `arrived`（已到达）→ `POST .../travel/claim` 领积分，再复查状态；
3. `idle` 且**未达每日上限** → `POST .../travel/depart` 派出（随机地点，或指定）；
4. `traveling` → 不派遣，只报到达倒计时；**已到达的奖励不会丢**，下次运行自动补领。

硬规则：派遣前必查 `daily_limit_reached`，达上限**一个写请求都不发**。
旅行接口域名固定 `www.workbuddy.cn` 且路径**不带 `/v2`**（用签到域名或加 `/v2` 一律 404）。

## 活跃自检与连登预警（v1.0.2 新增）

### 「签到」和「连登」是两套独立机制，别混为一谈

| | 签到 | 连登（streak / 活跃地图） |
|---|---|---|
| 接口 | `POST /v2/billing/meter/daily-checkin` | `GET /v2/activity/growth/streak`、`GET /v2/activity/growth/heatmap` |
| 给什么 | Credits（通用积分） | 决定 7 / 14 / 28 天档位的兑换奖励与补登卡 |
| 判定口径 | 手动/自动点「领取」 | **当天需完成一次有效对话** |
| 数据刷新 | 即时 | 活跃地图「每日 02:00」聚合 |

口径来源于成长计划页内置的官方文案（非推测）：

> 「活跃口径：需完成一次有效对话才能被记录至活跃地图。」
> 「为判定用户任务完成状态、计算能量值及积分（Credit），腾讯云需要收集：（1）**AI 对话次数**；…」

**结论：只跑签到脚本并不能保住连登。** 某天完全没用 WorkBuddy，活跃地图当天记 0 分，连登就断。

### 本工具怎么做

只读拉两个接口，逐账号报出「今日是否点亮 + 活跃分 + 连登天数」：

```
GET https://www.workbuddy.cn/v2/activity/growth/heatmap
    → data.today = {date, score, is_active, status_text}
GET https://www.workbuddy.cn/v2/activity/growth/streak
    → data.streak = {days, month_total_days, next_tier, makeup_dates}
```

活跃分档位（对齐前端配色函数）：`0` 未点亮 ｜ `≤10` 微亮 ｜ `≤30` 常亮 ｜ `≤60` 高亮 ｜ `>60` 炽热。
**当天未点亮时**，报告会打印 `⚠ 连登预警`，桌面通知标题也会变成「活跃预警：N 个账号今日未点亮」，并点名要手动处理的账号。

### 刻意没有做的事

**不代发对话、不调用任何模型接口。** 该活动条款明确写着：

> 「合规性要求：用户需通过正常使用路径参与活动，**严禁采用刷量、多账号套利、篡改数据等作弊行为**。一经系统识别，立即取消获奖资格，追回已发礼品。」
> 「如因账号异常、作弊行为、批量注册或**非正常使用路径触发风控**，平台有权取消领取资格并回收对应奖励权益。」

用脚本每天自动发一句「你好」去凑活跃，在风控视角下属于「刷量 / 非正常使用路径」，代价（取消资格 + 追回奖励 + 账号风险）远大于收益。所以本工具在活跃维度**只做检测与提醒**：发现没点亮就喊你一声，一条消息的事，自己发。

## 配置说明（`accounts.json`）

```json
{
  "version": 1,
  "settings": {
    "domains": ["www.workbuddy.cn", "www.codebuddy.cn"],
    "concurrency": 4,
    "travel_default": true,
    "desktop_notify": true
  },
  "accounts": [
    {
      "id": "acc1",
      "label": "张三",
      "uid": "…",
      "token": "<accessToken>",
      "domain": "www.workbuddy.cn",
      "enabled": true,
      "travel": true,
      "location_id": null
    }
  ]
}
```

- `domains`：候选域名，按顺序探测（本机实测 `www.workbuddy.cn` 可用；`copilot.tencent.com` 在旧版快照里作过日志域名）。
- `enabled: false`：临时停用某账号（菜单 `7 → 4` 可切换，不删配置）。
- `location_id`：该账号固定派遣地点；填 `null` 走随机。

## 排错速查

| 现象 | 原因与处置 |
|---|---|
| `Token 已失效或被拒绝（HTTP 401/403）` | Token 过期。登录该账号的 WorkBuddy 客户端 → 菜单 `7 → 1`（或 `--capture`）重新提取 |
| 菜单顶部显示 `Token：有 N 项需处理` | 有 Token 已过期或 7 天内到期，提前重新 capture 一次 |
| `无法连接签到接口（所有候选域名均失败）` | 内网/代理/防火墙；用菜单 `12` 看 DNS 是否解析成功 |
| `今日已签到，跳过领取` | 正常。服务端幂等，不会重复发积分 |
| `领取被服务端拒绝 code=10001 …（假已签到）` | **不正常，务必处理**：服务端在日边界对**未签到**的账号返回了「今天已签到」（读接口同期仍显示未签到）。v1.0.1 会先回查状态复核、再按 30/60/120 秒重试 3 次；若仍失败会明确报失败（退出码 1 + 桌面通知），此时需**手动补签**。旧版 v1.0.0 会把这种情况误当成功，请勿使用 |
| `今日派遣次数已用完，跳过派遣` | 正常的服务端每日限额，次日自动恢复 |
| `arrived` 状态一直不领 | 不会丢积分，下次运行自动补领 |
| CSV 里「已结算连签天数」比实际少 1 天 | 正常。该列取自状态接口，是**已结算口径**、当日入账可能滞后数分钟；判断当天签没签请只看 `状态/动作` 列或 `today_checked_in` |
| `⚠ 连登预警：以下账号今日未活跃` | **不是脚本出错**。该账号当天还没在 WorkBuddy 里完成过一次有效对话，活跃地图没记分，连登会断档。打开客户端任意对话发一条消息即可点亮；本工具只提醒、不代发（原因见上文「刻意没有做的事」） |
| `活跃：自检失败 — 活跃地图接口不可用` | 该接口按账号鉴权，Token 失效或网络异常都会这样。签到结论不受影响；先按上一条排查 Token |
| CSV 里的 `今日活跃 / 活跃分 / 连登天数` 三列是空的 | 你在跑 `--no-activity`，或者该行是**旧月份文件**写的。新列只出现在 v1.0.2 之后**新建**的月度文件里，旧文件仍按其原有表头写、不会串列 |
| 菜单里中文显示成乱码 | 用 `启动菜单.bat` 启动（它会切到 UTF-8 代码页）；不要在旧版 cmd 里直接跑 |
| 菜单每次刷新都要等约 1 秒 | 首次查询计划任务状态会启动一次 PowerShell，结果缓存 20 秒，属正常 |
| 计划任务没跑 | 任务在当前用户上下文注册，需用户已登录；菜单 `8 → 3` 看上次执行时间与结果 |

## 安全约定

- `accounts.json` 含**明文 Token**，是本工具唯一的凭据文件：不要外传、不要提交到代码仓库、不要放进共享目录。
- 所有输出（终端 / CSV / JSON / 桌面通知）中的 Token 一律脱敏为 `eyJhbGci...xxxx`。
- 写操作仅限 3 个已验证端点：`daily-checkin`、`travel/claim`、`travel/depart`。
  **活跃自检（heatmap / streak）全程只读**，不发任何写请求、不调用模型接口。
- 使用范围：**仅限本人账号**。

## 已知限制

- **Token 有效期约 30 天**，到期必须重新获取（本机实测 26 天左右）。这是接口鉴权的前提，无法绕过：
  桌面端 5.6+ 已把 accessToken / refreshToken 以 AES-256-GCM 静态加密存储，密钥只在客户端进程内存里、不落盘，离线无法解密。
  → 实用做法：每月登录一次客户端，跑一次 `--capture` 即可（工具会按账号自动择优更新）。
- 计划任务在「用户已登录」时触发；配合 `-StartWhenAvailable`，错过的执行会补跑一次。
- 旅行接口若被服务端下线，工具会静默降级，**不影响签到结论**。
- 未实现自动续期（refreshToken 同样被静态加密，无法离线使用）。

## 更新日志

### v1.0.2（2026-09-30）

**新增**：活跃自检（连登预警）—— 解决「只签到保不住连登」的问题。

- 查清一件容易误解的事：**签到 ≠ 连登**。签到走计费接口发 Credits；连登（`/v2/activity/growth/streak`）是**活跃地图的连续活跃天数**，口径是「当天完成一次有效对话」，每日 02:00 聚合。两者接口、机制完全独立。
- 新增只读自检：`GET /v2/activity/growth/heatmap` 取当日 `score / is_active`，`GET /v2/activity/growth/streak` 取连登天数与补登卡；逐账号打印，并写入 `logs/last_run.json` 的 `activity` 字段与 CSV。
- 新增「未活跃」预警：报告打印 `⚠ 连登预警` 并点名账号，桌面通知标题改为「活跃预警」，正文提示「请手动发一条消息保住连登」。
- 新增开关：`--activity-only`（只做活跃自检）、`--no-activity`（跳过）；菜单新增第 5 项「只做活跃自检（连登中断预警，只读）」，原 5–12 项顺移为 6–13，相关指引文案已同步。
- CSV 新增三列 `今日活跃 / 活跃分 / 连登天数`。**列定义按文件首行表头自适应**：新增列只写进 v1.0.2 之后新建的月度文件，历史月份旧文件仍按原表头写、不串列（已离线验证 16 列新文件与 13 列旧文件两种路径）。
- **明确不做的事**：不代发对话、不调用模型接口。活动条款写明「严禁采用刷量、多账号套利、篡改数据等作弊行为」「非正常使用路径触发风控，平台有权取消领取资格并回收奖励」，故活跃维度只做检测 + 提醒。
- 边界：活跃自检失败**不影响签到结论**（仅留痕），只有 `--activity-only` 模式下整体状态才由活跃接口决定。

### v1.0.1（2026-09-28）

**修复**：领取接口返回 `code=10001 / 已签到` 时不再直接当成功。

- **改前（v1.0.0）**：把该响应一律判为 `already_signed` 并静默结束 —— 一旦服务端在日边界返回了错的「已签到」（读接口同期仍显示未签到），当天就**漏签且无任何告警**，CSV / 通知 / 退出码全部报成功。
- **改后**：强制回查状态接口复核。复核也是已签 → 真幂等；复核仍是未签到 → 判为服务端「假已签到」，按 30/60/120 秒间隔重试（最多 4 次领取）；全部失败则 `status=error / action=rejected`，退出码 1 并在桌面通知中点名该账号，提示手动补签。
- 状态与领取接口的**原始 HTTP 码与响应体全部落盘**到 `logs/last_run.json` 的 `detail` 字段（改前恒为 `null`，事后无法定位），失败时也会打印到控制台。
- CSV 列名 `连续天数` → **`已结算连签天数`**（该字段为已结算口径，当日可能滞后）。
